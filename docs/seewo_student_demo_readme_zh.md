# Seewo 学生个体状态追踪 Demo 截图说明

本文档用于在不提供本机网址的情况下介绍当前 Demo。截图来自本地运行页面，适合发给团队、经理或校方做初步说明。

> 注意：当前 Demo 是本机原型，不把本机调试地址作为对外共享地址写入材料。若后续需要任意电脑访问，需要部署到局域网服务器或云服务器，并加入权限控制和数据脱敏。
> 如果 Markdown 预览器无法显示图片，请直接打开同目录下的 `seewo_student_demo_readme_zh.docx` 或 `seewo_student_demo_readme_zh_embedded.html`；这两个版本已经把图片嵌入文件内部。

## 1. Demo 一句话定位

本 Demo 是一个基于 Seewo 课堂视频和评课报告的“单学生状态追踪与课堂支持动作建议”原型。

它不是替代 Seewo，也不是医学诊断系统，而是在 Seewo 已有课堂数据基础上继续做三件事：

1. 从课堂整体数据下钻到某一个学生。
2. 从课后评课扩展到学生个体状态追踪。
3. 从状态识别进一步输出屏幕、语音、机器人动作和老师端提醒。

核心闭环：

```text
Seewo 课堂视频 / 评课报告 / 课堂声音
  -> 目标学生定位
  -> 30 秒时间窗口状态估计
  -> 关键片段复核
  -> 屏幕/语音/机器人/老师端动作建议
  -> 老师校正
  -> 个体化学生追踪数据库
```

## 3. 图 1：Demo 首屏总览

![Demo 首屏总览](assets/seewo_student_demo/demo_01_overview.png)

### 这张图要说明什么

这张图展示的是 Demo 的整体产品形态。页面分为三栏：

- 左侧：学生画像与数据来源。
- 中间：学生支持结论。
- 右侧：复核与执行建议。

顶部文案强调本系统的闭环：

```text
课堂视频/评课报告 -> 单学生状态估计 -> 低刺激支持动作 -> 老师复核反馈
```

这个设计的重点是把项目从“做一个识别模型”提升成“面向辅读学校课堂的具身智能支持系统”。也就是说，系统不仅判断学生状态，还要把结果转成可以执行的课堂支持动作。

### 左侧区域含义

左侧展示目标学生和数据来源：

- 使用 Seewo 导出的课堂视频作为原始输入。
- 使用 Seewo 评课报告作为课堂背景。
- 使用目标学生截图或人工 ROI 确定追踪对象。
- 当前样例课程约 38 分钟，视频规格为 960x544。
- 系统从 77 个 30 秒片段中筛选出建议老师复核的关键片段。

这里想表达的是：学校不需要一开始重新部署大量硬件，先利用已有 Seewo 数据就可以做第一版原型。

### 中间区域含义

中间展示本节课对目标学生的整体支持结论：

- 课堂参与基线：当前约 74% 的窗口保持参与线索。
- 需要支持窗口：系统筛出一批可能需要一步提示、视觉提示或观察的片段。
- 老师复核建议：成人遮挡、疑似困惑、注意力下降等片段优先交给老师确认。
- 主要执行动作：当前多数片段建议保持节奏，少数片段建议轻量提示。

这说明 Demo 的关注点不是简单地给学生贴标签，而是帮助老师找到“哪些时刻值得看一眼”。

### 右侧区域含义

右侧是具身智能动作输出区域，当前选中的片段会生成：

- 屏幕端动作：例如只保留当前一步、弱化无关信息。
- 语音端动作：例如“没关系，我们先看第一步。”
- 机器人动作：例如慢转向、轻微点头。
- 老师端提醒：是否需要老师确认。

这里是项目区别于普通课堂分析系统的关键：最终不是只输出分析结论，而是落到可执行动作。

## 4. 图 2：学生画像、课堂资料和支持计划

![学生画像与支持计划](assets/seewo_student_demo/demo_02_student_profile_and_support.png)

### 这张图要说明什么

这张图更适合讲“这个系统怎么跟学生长期追踪结合”。

左侧可以看到学生追踪档案：

- 匿名学生 ID。
- 当前阶段：初始基线建立中。
- 已接入资料：课堂视频和评课资料。
- 后续待补资料：学生测评档案、既有行为指导、有效提示方式、禁忌刺激。

这说明当前系统不是只分析一节课，而是准备建立每个学生的长期个体档案。

### 为什么要接入 Seewo 评课报告

Seewo 评课报告提供的是课堂整体背景，例如：

- 课程名称。
- 学科。
- 教师。
- 抬头率。
- 参与度。
- 平均语速。

这些信息不能直接等同于某一个学生的真实状态，但可以帮助系统判断当前片段处在什么课堂环境中。例如同样是学生动作少，如果当时老师正在讲解或等待回答，含义就可能不同。

### 下一次课堂支持重点

系统会输出下一次课堂建议，例如：

- 请老师优先复核关键片段。
- 补充学生测评档案和行为指导。
- 下一节课继续追踪同一学生，比较参与稳定性和需要支持片段数量。
- 动作输出先以屏幕弱高亮、一步提示、老师端提醒为主，不做突然动作。

这部分非常重要，因为它把 Demo 从“一次性分析”变成“持续追踪和迭代”。

## 5. 图 3：完整时间窗口与动作建议

![完整窗口与动作建议](assets/seewo_student_demo/demo_03_windows_and_action_panel.png)

### 这张图要说明什么

这张图展示系统如何把一整节课拆成可复核、可训练、可追踪的时间窗口。

当前 Demo 将约 38 分钟课堂视频切成 77 个 30 秒窗口，每个窗口会给出：

- 起止时间。
- 当前状态。
- 置信度。
- 状态颜色。
- 是否属于关键复核片段。

这比只给一个“整节课参与度”更有价值，因为老师可以知道问题或变化发生在什么时候。

### 状态窗口有什么用

这些窗口后续可以成为训练数据的基本单位：

1. 系统先自动给出弱标签。
2. 老师只复核关键片段，而不是看完整节课。
3. 老师选择“符合观察 / 需要修正 / 不确定”。
4. 复核结果进入训练数据库。
5. 后续模型用这些校正标签继续训练。

这样可以解决真实学校数据少、老师没时间做大量标注的问题。

### 右侧动作建议有什么用

右侧保留当前片段的动作建议，例如：

- 当前状态：困惑/停滞。
- 建议动作：一步视觉提示。
- 屏幕：只保留当前一步，弱化无关信息。
- 语音：没关系，我们先看第一步。
- 机器人动作：慢转向屏幕并轻微点头。
- 安全边界：先交给老师确认，避免误打断学生。

这说明本项目后续可以接机器人、学生端屏幕或老师端提醒系统。

## 6. 图 4：结构化 JSON 输出

![结构化 JSON 输出](assets/seewo_student_demo/demo_04_structured_json_output.png)

### 这张图要说明什么

这张图展示 Demo 不是静态页面，而是有结构化数据输出。

当前 JSON 中包含：

- `target_student`：目标学生信息和 ROI。
- `video_meta`：视频时长、分辨率、帧率。
- `report_summary`：Seewo 评课报告摘要。
- `timeline`：完整 30 秒状态窗口。
- `aggregate`：整节课聚合统计。
- `student_tracking`：学生个体追踪结论。
- `recommended_action`：屏幕、语音、机器人和老师端动作建议。

结构化输出的意义是：

- 可以存入学生追踪数据库。
- 可以作为老师复核工作台的数据源。
- 可以提供给 WebSocket 或 ROS2。
- 可以成为后续训练模型的数据格式。
- 可以接入机器人策略层。

## 7. 当前使用的模型和算法

当前版本是可解释 baseline，不是最终深度学习模型。

### 7.1 视频侧

使用：

```text
OpenCV
```

当前能力：

- 读取 Seewo 导出视频。
- 按时间抽帧。
- 对目标学生 ROI 计算动作变化。
- 对老师/成人区域计算遮挡或干扰。
- 估计画面亮度和清晰度。

当前不做：

- 精细表情识别。
- 稳定眼神追踪。
- 自动多学生身份识别。

原因是当前 Seewo 全景视频清晰度有限，第一版更适合做粗粒度行为和状态追踪。

### 7.2 音频侧

使用：

```text
ffmpeg / imageio-ffmpeg
```

当前能力：

- 从课堂视频中抽取音频。
- 按窗口计算声音活跃度。
- 辅助判断课堂声音活跃但目标学生动作少的片段。

后续可以升级：

- Whisper / faster-whisper 做 ASR。
- 语速、音量、停顿分析。
- 异常声音事件检测。
- 粗粒度说话人区分。

### 7.3 课堂报告侧

使用：

```text
python-docx
```

当前能力：

- 解析 Seewo 评课详情文档。
- 提取课程时长、参与度、抬头率、平均语速等信息。
- 为学生状态分析提供课堂上下文。

### 7.4 状态估计和动作决策

当前状态估计使用规则 baseline，输出：

- 参与。
- 注意力下降。
- 困惑/停滞。
- 成人干扰下不确定。

当前动作决策使用规则策略库，输出：

- 屏幕提示。
- 语音提示。
- 机器人动作。
- 老师端提醒。

这是为了先跑通完整闭环，后续再替换为可训练模型。

## 8. 后续训练路线

真实学校数据通常一开始很少，所以不建议直接训练大模型。更合理的路线是：

```text
规则 baseline
  -> 老师复核关键片段
  -> 小样本训练数据
  -> 轻量分类模型
  -> 姿态/语音增强
  -> 个体化学生追踪模型
  -> 具身动作策略模型
```

第一阶段优先训练：

- Logistic Regression。
- Random Forest。
- LightGBM / XGBoost。
- 简单 GRU / TCN。

后续再引入：

- MediaPipe Pose 或 YOLO Pose。
- ByteTrack / DeepSORT。
- Whisper ASR。
- 行为克隆或轻量强化学习动作策略。
- 更大的 VLM/VLA 模型用于动作规划或场景理解。

## 9. 算力要求

### 9.1 当前 Demo 展示

当前展示不需要 GPU。

| 任务 | 推荐配置 | 是否需要 GPU |
| --- | --- | --- |
| 打开已生成 Demo | 4 核 CPU，8 GB 内存 | 不需要 |
| 重新分析一节 30-40 分钟视频 | 4-8 核 CPU，8-16 GB 内存 | 不需要 |
| 多节课批量抽帧和音频能量分析 | 8 核 CPU，16 GB 内存 | 可选 |

当前样例约 38 分钟，系统不是逐帧跑深度模型，而是抽帧加窗口聚合，所以普通电脑可以运行。

### 9.2 轻量模型训练

| 任务 | 推荐配置 | 是否需要 GPU |
| --- | --- | --- |
| 规则阈值调参 | 8 GB 内存 | 不需要 |
| Logistic Regression / Random Forest | 8-16 GB 内存 | 不需要 |
| LightGBM / XGBoost | 16 GB 内存更稳 | 不需要 |
| 小型 GRU / TCN | 16 GB 内存 | 可选 GPU |

如果只是 5-20 名学生、几十节课以内，本机训练足够。

### 9.3 姿态识别、ASR 和更大模型

| 任务 | 推荐算力 |
| --- | --- |
| MediaPipe Pose 单路视频 | 本机 CPU 可跑 |
| YOLO Pose 离线批处理 | 建议 RTX 3060/4060 或云 GPU |
| Whisper tiny/base | 本机可跑，但速度较慢 |
| Whisper small/medium | 建议 6-12 GB 显存 |
| 多节课批量 ASR 和姿态识别 | 建议云服务器 |
| VLM/VLA 本地推理或微调 | 后期再做，建议 24 GB 显存起步或云端 |
| Isaac Sim 仿真 | 建议 NVIDIA RTX GPU 或云电脑 |

### 9.4 什么时候需要云服务器

短期做 Demo 和小样本 baseline 不一定需要云服务器。

开始需要云服务器的时间点：

1. 需要让团队或校方通过公网访问。
2. 需要批量处理多节课视频。
3. 需要批量跑 ASR。
4. 需要跑 YOLO Pose 或多学生追踪。
5. 需要上线学生追踪数据库。
6. 需要跑 Isaac Sim 或更重的具身仿真。
7. 需要训练较大的时序模型、VLM 或 VLA 相关策略模型。

## 10. 数据和隐私边界

真实学生数据必须谨慎处理：

- 需要学校授权。
- 需要家长授权。
- 对外展示必须匿名化。
- 不公开学生姓名、清晰头像、完整视频和原始声音。
- 不做医学诊断。
- 专业评估和行为指导只能作为安全约束和个体化支持背景。
- Demo 页面如果部署到公网，必须加权限控制。

## 11. 推荐讲法

可以这样介绍当前 Demo：

```text
这个 Demo 不是替代 Seewo，而是基于 Seewo 已经有的课堂视频和评课报告，继续往学生个体支持层做延伸。

Seewo 更擅长记录一节课发生了什么，本系统关注某一个学生在这节课里什么时候可能需要支持、为什么需要支持，以及下一步屏幕、语音、机器人或老师端应该做什么动作。

当前版本先用可解释 baseline 跑通闭环，后续通过老师复核关键片段形成训练标签，再逐步升级到姿态识别、语音识别、个体化数据库和具身动作策略。
```

## 12. 当前限制

需要主动说明：

- 当前不是最终训练模型，而是可解释 baseline。
- 当前目标学生 ROI 是人工设定。
- 低清全景视频不适合做精细表情和眼神识别。
- 音频目前只做声音活跃度，尚未做完整 ASR。
- 当前结论是课堂支持参考，不是医学诊断。
- 后续必须依赖老师复核，形成真正可训练的数据集。
